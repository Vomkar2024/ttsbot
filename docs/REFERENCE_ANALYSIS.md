# Discord TTS Bot — Technical Reference Analysis

## 1. System Architecture

Discord TTS Bot is an offline, self-contained Discord Text-to-Speech service designed for low-latency, deterministic audio playback without reliance on third-party cloud APIs.

```
                      +-----------------------------+

[format-message]   [settings-store]         [session-manager] [settings-store]
     | (Clean Text)      | (Preferences)           | (Join/Leave)  | (Configure)
```

## 2. Audio Pipeline & Synthesis Protocol

### 2.1 eSpeak NG Interprocess Streaming
- Text is delivered to `espeak-ng` via `stdin` to prevent shell argument limits, command-injection vulnerabilities, and character-escaping issues.
- The command invocation pattern:
  ```bash
  espeak-ng -v <voice> --stdin --stdout [-s <speed>] [-p <pitch>]
  ```
- Output is emitted as standard RIFF/WAVE PCM audio on `stdout`.
- Cancellation is handled via Node's `AbortController` / `AbortSignal`:
  - When a message is skipped or stopped, `SIGTERM` is dispatched to the child process.
  - Subprocess file handles (`stdin`, `stdout`, `stderr`) are closed cleanly to release OS descriptors immediately.

### 2.2 Transcoding to Discord Voice
- `@discordjs/voice` handles voice UDP framing.
- The WAV stream generated by eSpeak is piped into `createAudioResource(stream, { inputType: StreamType.Arbitrary })`.
- FFmpeg transcodes raw 22.05kHz/16-bit mono PCM into 48kHz stereo PCM, which the Opus encoder (`@discordjs/opus` or fallback `opusscript`) compresses into 20ms frames for transmission over encrypted UDP sockets.

## 3. Serial Queue & State Machine

Each guild maintains an isolated `SerialQueue` instance to guarantee non-overlapping, strictly ordered speech synthesis and playback:

```
                  +--------------+
                  |     Idle     |
                  +-------+------+
                          |
             enqueue()    |
                          v
                  +--------------+
      +---------->| Synthesizing |
      |           +-------+------+
      |                   |
      |                   v
      |           +--------------+
      |           |   Playing    |
      |           +-------+------+
      |                   |
      |      Playback     |
      |      Complete     v
      |           +--------------+
      +-----------+ Next in FIFO |
      (if items)  +-------+------+
                          |
                          v (empty)
                  +--------------+
                  |     Idle     |
                  +--------------+
```

### 3.1 Queue Control Operations
- **`skip()`**: Aborts the active job's `AbortSignal`. The audio player is immediately stopped (`audioPlayer.stop(true)`), terminating both synthesis and playback for the current item. The FIFO processor immediately advances to the next waiting item.
- **`stop()`**: Aborts the current job's `AbortSignal` and rejects/drains all pending items in the waiting list with `AbortError`. The queue transitions to `Idle`.
- **`clear()`**: Drains and rejects all pending items in the waiting list with `AbortError` while leaving the currently playing item uninterrupted.
- **Error Isolation**: If an individual job fails (e.g. malformed unicode or temporary process error), that specific job's promise is rejected, and the queue continues with the next job in FIFO order without stalling.

## 4. Voice Session Concurrency & Lifecycle

### 4.1 Per-Guild Concurrency Locks
Voice connection state transitions (such as `join` and `leave`) are asynchronous and susceptible to race conditions if multiple users execute commands concurrently. `VoiceSessionManager` serializes operations per guild using a promise chain:
```javascript
async _serialize(guildId, task) {
  const prev = this.guildLocks.get(guildId) || Promise.resolve();
  const current = prev.catch(() => {}).then(task);
  this.guildLocks.set(guildId, current);
  return current;
}
```

### 4.2 Lifecycle Transitions
1. **Same-Channel Joins**: If `/join` is executed for a voice channel where an active, healthy session already exists, the bot retains the existing connection and returns `{ reused: true }`.
2. **Channel Switches**: If the bot is already connected to Channel A and `/join` is invoked in Channel B, the old session is destroyed cleanly (purging old queue and connection) before opening Channel B.
3. **Transient Disconnect Grace**: Network jitter or Discord server migrations trigger `VoiceConnectionStatus.Disconnected`. A grace timer (`VOICE_DISCONNECT_GRACE_MS`, default 8000ms) permits automatic reconnection before destroying the session.

## 5. Storage Engine & Preference Resolution

### 5.1 Native SQLite
The bot uses built-in SQLite (`sqlite3`), eliminating external database servers or native C++ compilation modules.

### 5.2 Schema Architecture
```sql
CREATE TABLE IF NOT EXISTS guild_settings (
  guild_id TEXT PRIMARY KEY,
  channel_id TEXT,
  default_language TEXT,
  default_voice TEXT,
  updated_at INTEGER
);

CREATE TABLE IF NOT EXISTS user_settings (
  guild_id TEXT,
  user_id TEXT,
  language TEXT,
  voice TEXT,
  updated_at INTEGER,
  PRIMARY KEY (guild_id, user_id)
);
```

### 5.3 Field-by-Field Precedence Resolution
Preferences resolve independently field-by-field:
- **Language**: `User Override` > `Server Default` > `Global Default ('en')`
- **Voice Variant**: `User Override` > `Server Default` > `Global Default ('default')`

```
User Preference:     { language: 'fr', voice: null }
Server Default:      { language: 'es', voice: '+m1' }
Effective Profile:   { language: 'fr', voice: '+m1' }
```
